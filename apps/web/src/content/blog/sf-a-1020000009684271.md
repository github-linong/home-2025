### 解答思路
`setTimeout` 设置的毫秒数并不是“精确的执行时间”，而是“多久之后可以被放入任务队列等待执行”；只有当前同步代码（包括被 `alert` 阻塞的那段）全部执行完毕，JS 引擎才会去看队列里有没有到时间的回调可以执行。

### 示例代码
```js
for (var i = 0; i < 5; i++) {
  // 延迟执行
  setTimeout(function () {
    console.log(new Date(), i);
  }, 1000);
}

console.log(new Date(), i);

alert("我们用 alert 挂起一下程序，你等待两三秒再确定");
// 执行到这里，这个同步队列才算是执行完了。
// 然后才会尝试执行 setTimeout 延时的回调，看看是否已经到时间可以调用了。
```

### 详细说明
- 循环体内的 `setTimeout` 只是把回调“预约”进任务队列，1000ms 后到期，但到期并不代表立刻执行，而是“有资格被执行”。
- `console.log(new Date, i)`（循环外）会在循环结束后立刻同步执行，此时 `i` 已经是 `5`。
- `alert` 会阻塞主线程，只要弹窗没被关闭，JS 引擎就无法去处理任务队列，哪怕 `setTimeout` 的 1000ms 早就到了。
- 等 `alert` 被确认关闭、同步代码执行完毕后，引擎才会依次把队列中已到期的 5 个 `setTimeout` 回调拿出来执行，此时它们打印的时间会明显晚于“预约”时的时间，而 `i` 的值则和闭包捕获的变量有关（`var` 声明下 5 次回调共享同一个 `i`，此时都已经变成 `5`）。

### 小结
`setTimeout` 只保证“不早于”指定时间执行，真正的执行时机还要看主线程何时空闲；如果主线程被同步代码或 `alert` 阻塞，异步回调只能排队等待，这正是 JS 单线程 + 事件循环模型的核心体现。
