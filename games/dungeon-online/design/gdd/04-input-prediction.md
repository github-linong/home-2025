# GDD ④ 输入与客户端预测系统（Input & Client Prediction）
**路径**：`games/dungeon-online/design/gdd/04-input-prediction.md` ｜ 标记：`[MVP][P3]`
**依赖（systems-index §2）**：依赖 ① 联机与房间（L1→L0）；被依赖 ⑦⑧⑩⑬。

## 1. 目的与支柱对齐
解决玩家操作在网络延迟下仍"跟手"，并能被服务器权威回正。直接服务 **P3「读得懂的紧张感」的延迟宽容体验下限**（concept §1 P3：用可读局势张力而非硬核反应作难度，宽容延迟）。是 ⑦战斗 / ⑨协作技 / ⑩信号 / ⑪救援 的操作入口。

## 2. 依赖与上游接口
- **依赖**：① 联机与房间（传输 + 权威状态容器 + 下发 diff）。
- **提供接口（被依赖方）**：
  - → ⑦ 战斗：输入指令流（移动向量、攻击、闪避、技能触发），战斗据指令在服务器结算。
  - → ⑩ 信号：ping/表情等信号指令经此上报。
  - → ⑬ HUD：本地预测状态（自身位置平滑）+ 延迟指示（来自联网）。
- **上游接口需求（→程基岩）**：tick rate / RTT 容忍 / 输入 schema / 状态 diff 格式 / 回正插值（systems-index §5 ④）。

## 3. 核心机制
- **输入采样**：每渲染帧采集本地输入（键鼠/触控），打包为"输入指令"（含 `sequence_id`、`tick` 戳、动作类型、参数如移动方向）。
- **本地预测**：收到输入即本地模拟角色位移/普攻表现（不等待服务器），保证跟手。
- **上报**：输入指令按网络帧上报服务器（含 `tick` 戳）。
- **服务器结算**：服务器按 tick 顺序应用全部玩家输入指令，算出权威状态。
- **回正(reconciliation)**：客户端收权威 diff 与本地预测比对；若偏差（被击退/伤害/服务器修正），以权威覆盖并**重演**本地未确认输入。
- **插值平滑**：对其他玩家/敌人，在两次权威快照间做实体插值，避免抖动。

## 4. 数值/平衡初稿（`待调`）
- **`TICK_RATE`：引用 `ADR-NET-01`（锁 30Hz），本系统不再单独定义。**
- 输入采样率：渲染帧(60fps)采样，按网络帧（≈每 tick 或 20Hz）上报，`待调`（由 `ADR-NET-01` 定节奏）。
- **RTT 容忍上限：250ms（"流畅"阈值）已锁 `ADR-NET-01`（D3）；>400ms 明显回正抖动。本值不再 `待调`。**
- 预测缓冲：保留最近 ~(`RTT/2` + 2 tick) 的输入指令用于重演。
- 插值延迟：~100ms（2–3 快照）缓冲，`待调`。

## 5. 状态机/流程
- 本地：`IDLE` → 采集输入 → 预测应用 → 上报 → 等权威。
- 收权威 diff → 比对 → 偏差? `回正重演` : `接受`。
- 表现层：本地玩家=预测+回正；远程玩家/敌人=插值。
- 断线：本地入"等待重连"表现（角色冻结/托管由 ①/⑪ 决定），输入丢弃至重连。

## 6. 联机/权威服务器影响
- 所有"有效性"判定在服务器：伤害/位移/闪避 i-frame 是否生效以服务器 tick 为准。
- 客户端预测仅表现层；回正保证最终一致，消除"我的操作没生效"感。
- **与 ⑦ 战斗回正对齐**：战斗结算结果（伤害/击退/状态）作为权威 diff 下发，本系统据其回正（契约见 ⑦ §8 / 本 §8）。

## 7. 可读性/UX 约束
- 延迟指示：HUD 显 ping(ms) + 连接质量（**图标+文字三重**，不靠色 alone），高延迟提示"延迟高，表现已平滑"降低误读。
- 预测/回正不得破坏 P3 可读：回正跳变须平滑（插值），避免角色瞬移误导读战局。
- 按键重映射：多人分键，输入系统须支持全功能键位重映射（art-bible §10 可访问性底线，Lean 不可砍）。
- **【跨 GDD 一致性约束 · P3 保底 · 已锁 ADR-NET-01（D3）】预警前摇与 RTT 容忍不等式**：所有危险 telegraph 的**预警前摇 ≥ max(P3 硬下限 0.6s, RTT 容忍上限 250ms + 表现余量 K 100ms)**。已锁 `ADR-NET-01`（D3）：RTT 上限 250ms + K 100ms = 350ms < 0.6s（600ms），**硬下限 0.6s 主导**；telegraph 下限 = 18 tick（@30Hz）。该不等式是 P3「读得懂的紧张感」在弱网下的保底条件——若预警前摇 ≤ RTT 容忍，高延迟玩家在预警尚未结束、服务器已结算伤害时才"看到"危险，可读紧张感崩塌。本约束与 ⑦ §7 / ⑧ §4、§7 同文，由 ⑦ 与 ⑧ 在时序上落地。

## 8. 开放问题与工程接口
- 引用 systems-index §5 ④：需程基岩 ADR（统一为 `ADR-NET-01`）。
- **设计层需求（交程基岩 `ADR-NET-01`）**：
  1. `TICK_RATE` 定值（**引用 ① 契约，不单独定义**）。
  2. RTT 容忍上限（设计建议 ≤250ms 流畅；与不等式余量 K 一并回填）。
  3. 输入指令 schema（`sequence_id`/`tick`/`action`/`param`）。
  4. 服务器→客户端状态 diff 格式（**format-owner = ①**，本系统为 consumer）。
  5. 回正/插值策略边界（预测缓冲时长、插值延迟）。
- **与 ⑦ 战斗的契约**：战斗结算结果经 ① 定义的 diff 格式下发，本系统作为 **consumer** 回正消费（producer=⑦, format-owner=①, consumer=本系统；角色见 ① §8）。
- **开放问题**：输入上报频率 vs Web 弱网带宽；移动端触控回退是否影响 schema？`待定`。
