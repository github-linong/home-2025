## 0. 元决策回顾（已锁定）
- 引擎：Godot 4
- 目标平台：Web 浏览器（短会话、高频次）
- 联机架构：权威服务器（authoritative server，服务器持权威状态）
- 评审强度：Lean 精简
- 类型方向：**动作 Roguelike（实时）为主轴**，吸收轻量 Build 构筑作局内决策纵深
- 美术风格：**像素风**
- MVP 匹配：**好友房 + 邀请优先**（随机匹配留延展）
- 本阶段：仅做方向层，不写具体系统

## 1. 游戏支柱（Design Pillars）
四条主支柱（刻意控量，避免支柱漂移）；轻量 Build 作为局内决策纵深融入玩法，不单列支柱。

**P1 — 四人同心，胜于孤勇（Co-op Synergy First）**
定位：所有核心张力来自小队配合而非个人变强，设计优先级永远把协同置于个人操作之上。
为何成立：联机是项目 DNA（2-4 人 + 权威服务器）。若把单人爽感放首位，联机就只是"多人各打各的"，服务器复杂度白白付出；只有把协同做成必需，联机才不可替代。

**P2 — 每局都是新谜题（Run-Based Variety）**
定位：每一局地牢在布局、敌人与资源上都有足够变化，让"再来一局"成为自然冲动而非任务。
为何成立：Web 天然是短会话高频次场景，run 结构最契合浏览器进出节奏；变化性能持续掩盖内容量不足（Lean 下预算有限）。此支柱也直接对抗"主导策略"红线——足够变化让单一 Build 无法通吃。

**P3 — 读得懂的紧张感（Readable Tension）**
定位：所有战斗与危机在 2D 画面中"一眼可读"，信息密度高但不糊；紧张来自局势而非视觉噪音。
为何成立：2D 俯视/侧视的强项是可读性与手感；叠加 Web 联机存在网络抖动，若玩法依赖像素级精确预判会被延迟放大并劝退。故用"可读的局势张力"而非"硬核反应"作难度来源——既护住 2D 优势又宽容延迟，规避"认知过载"红线。*（实现层须由程基岩出 ADR 明确延迟预算与可读性阈值，见文末风险。）*

**P4 — 断线即重连，战局不散（Drop-In / Drop-Out Resilience）**
定位：任何玩家掉线，小队与其角色状态由服务器保留，重连即归队，一局不因一人离开而崩。
为何成立：权威服务器天然持有完整权威状态，是"无缝重连"的前提；浏览器玩家更易因切后台/网络波动掉线，把容错做成支柱而非补丁，是 Web 联机留存底线。

> 轻量 Build 说明：局内决策纵深（职业/技能/下行路线/资源分配的选择）承载"轻量 Build 构筑"精神，自 MVP 起即存在；但正式 Build 系统（装备/perk 槽 + 局内掉落）按决策落到 MVP 之后的延展层，不另设支柱，以防支柱漂移。

## 2. MDA 框架分析
| 层 | 内容 |
|---|---|
| **Mechanics（机制/规则层 · 设计师视角）** | ① 小队进入"地牢房间"(session/room)，逐层下行；② 角色具位移、普攻、1-2 主动技、1 协作技；③ 敌人与陷阱按层生成，资源（药品/弹药/增益）有限；④ 死亡非终局——本局内可救援/复活队友（服务器托管状态）；⑤ 权威服务器结算所有伤害与状态，客户端仅预测表现；⑥ 房间有生命周期：集结→下行→Boss/出口→结算；⑦ 局内 Build 决策（职业/技能/路线/资源）构成轻量构筑纵深。 |
| **Dynamics（动态/涌现层 · 运行时行为）** | ① 四人分工自然涌现（坦/输出/辅助/控场），因协作技与有限资源强制配合；② "救不救队友"成为反复出现的策略/戏剧抉择；③ 掉线玩家角色由托管暂代或冻结，小队可继续推进，重连无缝；④ 资源稀缺驱动"谁拿增益/谁殿后"的实时谈判；⑤ 延迟下玩家形成"预输入+服务器回正"的独特联机手感；⑥ 轻量 Build 选择驱动每局差异化打法。 |
| **Aesthetics（美学/情感层 · 玩家感受）** | 主导：**Fellowship（同伴）** + **Challenge（挑战）**；辅助：**Discovery（探索）** + **Sensation（感官，像素地牢的阴森可爱）** + **Submission（沉浸，"再来一局"）**。声明：美学以 Fellowship+Challenge 为主导，不堆砌更多美学期，以防支柱漂移。 |

## 3. 核心循环（动词优先法）
- **微观核心动词（每帧/每秒）**：移动 → 瞄准/闪避 → 攻击 → 触发协作技
- **中观核心循环（每局 Run）**：
  探(Explore) → 战(Fight) → 拾(Loot) → 商(Negotiate/Regroup) → 下(Descend)
  回到"探"，直至 Boss/出口 或 团灭。
- **宏观循环（跨局 Meta）**：
  出征(组队/选 Build) → 下副本(Run) → 结算(得失) → 成长(解锁/构筑) → 再出征

**权威服务器对核心循环的方向层影响（不写系统）：**
- "探/战/拾"的状态判定全在服务器，客户端为表现层 → 循环设计须保证"服务器一帧裁定"颗粒度够细，避免"我的操作没生效"感（客户端预测+服务器回正属实现层）。
- "商(Regroup)"在联机下是实时协作谈判，需预留情绪沟通窗口（安全屋/层间休息点），否则协同支柱落空。
- "断线重连"作为循环异常分支：服务器持有角色权威状态，掉线不终止循环，重连归入"商/探"节点。核心循环在概念上必须允许"成员动态进出"，而非假定 4 人恒定在场。

## 4. 玩家心理学
### 4.1 自我决定论（SDT）三需求
- **自主(Autonomy)**：每局选角色/Build、选下行路线（分支房间）、选资源分配 → "我在做有意义的决定"；Meta 层解锁顺序也留选择。
- **胜任(Competence)**：难度曲线（§4.2）让玩家"跳一跳够得着"；协作技成功、救起队友、首通 Boss 提供强胜任反馈；服务器权威结算保证公平，避免"赢了却被延迟坑"的胜任感破坏。
- **关联(Relatedness)**：协同支柱直接服务——救援机制、协作技、共享资源谈判、小队存续强化"我们是一伙的"；好友房+邀请优先契合强关系起点。

### 4.2 心流平衡（Flow）难度曲线
- 每层即心流单元：前 1-2 层低唤醒（热身），中段引入新敌人组合拉升挑战，Boss 层为尖峰。
- 难度来自"局势复杂度"（敌人种类/配合要求）而非"数值碾压"或"反应阈值"，以宽容 Web 延迟（呼应 P3）。
- 动态难度（可选/延展）：服务器按小队平均表现微调后续层密度，避免"一人在拖全队"心流断裂——MVP 不做，防过度设计。
- 断线重连降低"非自愿心流中断"，保护沉浸。

### 4.3 Bartle 玩家类型映射
- **Socializer（社交者）**：核心受众。协同、救援、小队沟通、好友房满足其主导需求；本作最倚重。
- **Achiever（成就者）**：Boss 首通、层深纪录、Meta 解锁、成就系统满足。
- **Explorer（探索者）**：程序化地牢的布局/隐藏房/机制发现满足。
- **Killer（杀戮者）**：非核心。未来若加 PvPvE/竞速排行可少量覆盖，但 MVP 不做 PvP，以免与"关联/协同"支柱冲突（防支柱漂移）。
- **结论**：目标画像 = Socializer 为主 + Achiever/Explorer 为辅，Killer 不在 MVP 范围。

## 5. 范围分层（Scope Layering）
### MVP（最小可玩，验证核心支柱）
包含：
- 1 种地牢生物群系（如"余烬矿坑"），固定模板 + 轻量随机（房间顺序/敌人点位）
- 4 基础职业（覆盖 坦/输出/辅助/控场 原型），各 1 主动 + 1 协作技
- 基础实时战斗：移动/普攻/闪避/技能，客户端预测 + 服务器权威
- **房间系统：好友房 + 邀请（2-4 人），房间码/链接分享**（*随机/快速匹配已移出 MVP，见延展*）
- 核心循环贯通：探→战→拾→商→下→Boss→结算
- 断线重连：服务器托管状态，重连归队
- 基础 HUD + 快捷信号（无语音也可协作）
- 局内 Build 决策纵深：职业/技能/路线/资源分配的选择（轻量构筑精神，MVP 不做装备/perk 系统）
- 单局时长目标：8–15 分钟（契合 Web 会话）

砍掉：程序化深度生成、多生物群系、Meta 持久成长、装备/perk Build 系统、PvP、赛季、mod、皮肤经济、语音内嵌、**随机/快速匹配**。

### 延展（Extended — 验证后迭代）
包含：
- 程序化地牢生成（提升 P2 重玩价值）
- 2-3 额外生物群系 + 主题敌人/Boss
- 轻量 Build 构筑系统（装备/perk 槽 + 局内掉落，非交易市场）+ Meta 解锁
- 轻量物品经济（局内掉落 + 局外存档，非交易市场）
- **随机/快速匹配（陌生人组队）**
- 动态难度、排行榜（非 PvP）、好友系统与邀请增强
- 内嵌语音 / 更丰富信号系统

砍掉：完整交易拍卖行、PvP 竞技、UGC/mod、跨平台（移动端）。

### 梦想（Dream — 愿景）
- 跨平台（Web + 桌面 + 移动）无缝同服
- PvPvE 模式（阵营抢夺/竞技地牢）
- 赛季制 + 大型叙事活动
- 官方 mod/UGC 工具链
- 皮肤/外观经济（不影响数值）
- 电竞/社区赛事支持

## 6. 视觉锚点（Visual Anchors — 交 art-director）
> 本节供 art-director 立项参考；design-strategist 仅给方向约束，不代行美术决策。**美术风格已锁定为像素风。**

- **美术风格（已锁定）：像素风（Pixel Art）**
  - **规格基准**：32px 基础瓦片网格（tile base）；源稿按 **2× 绘制**（即角色/物件以约 64px 当量起稿再规范缩至 32px 显示），保证高 DPI/视网膜屏上仍清晰不糊。
  - **滤波策略**：全程 **Nearest-neighbor（最近邻 / 点采样）滤波**，禁用双线性插值；缩放时像素硬边、不晕开。
  - **Web 友好理由**：① 像素小图文件体积极小 → 浏览器首屏加载快、带宽占用低；② Nearest 滤波 GPU 开销极低，中低端设备与弱网也能稳帧；③ 高 DPI 下靠 2× 源稿 + Nearest 保持锐利，无需大图；④ 像素风对"内容量不足"容忍度高（Lean 下美术产能友好），且小尺寸下轮廓仍清晰，直接服务 P3「读得懂的紧张感」；⑤ 产出迭代快，利于 Lean 评审节奏。
- **情绪基调(Mood)**：阴森中带温暖、危险中带可爱——"敌人很凶，但和队友在一起很安心"。紧张感来自光照与构图，而非血腥。
- **配色方向(Palette)**：
  - 地牢基底：低饱和冷色（炭灰、苔藓绿、暗蓝）营造地下压迫感
  - 暖色点缀：余烬橙/烛光黄作为"安全/希望/协作"信号色（呼应"余烬"）
  - 队伍识别：4 个高区分度、对色盲友好的队伍强调色（角色描边/协作技光效），保证 2D 联机下"谁是谁"一眼可读
  - Web 适配：避免纯黑背景（浏览器环境光干扰），用深灰蓝；高对比度保证可读性（呼应 P3）
- **参考意象 / 关键词(References & Keywords)**：
  - 关键词：pixel dungeon, candlelit, cozy-horror, readable 2D, ember glow, 32px tile
  - 意象：暖光烛火映照的石廊、队友技能交汇的光晕、敌人剪影而非写实血肉
  - 可读性硬约束：所有危险（敌人攻击前摇、陷阱、AOE）必须有明确轮廓/色块预警，不得靠细微动画暗示（服务 P3 + Web 延迟宽容）

## 7. 已锁定子类型决策（设计史留痕）
> 用户 2026-08-04 已拍板：**方案 A 动作 Roguelike 为主轴**，并吸收方案 B 的轻量 Build 构筑作局内决策纵深（落 MVP 后延展层，不单列支柱）。以下为当初三方案对比，标记采纳项。

**方案 A：动作 Roguelike（实时 / 反应向）✅ 已采纳（主轴）**
- 核心差异：实时动作战斗 + 每局（半）程序化地牢 + 死亡/团灭即结算；短局、高重开。
- 联机体验：4 人实时同屏协作，救援/协作技实时触发，最贴合"协同+可读紧张"双支柱；小队心跳时刻密集。
- 网络/实现：实时状态同步 + 客户端预测 + 服务器回正，netcode 复杂度中高；但 run 短，重连成本可接受。
- 参考：Hades（四人化）、Enter the Gungeon、Risk of Rain 2（2D 化）

**方案 B：ARPG / 地牢刷宝（实时 / 成长向）— 部分吸收（轻量 Build 精神）**
- 核心差异：实时战斗 + 强掉落/装备驱动 + 局外 Meta 成长。
- 处理：其"轻量 Build 构筑"精神被吸收为局内决策纵深与延展层 Build 系统；但 MVP 不做重 Meta 经济，避免"经济失衡"红线。

**方案 C：回合制地牢探险（回合 / 策略向）— 未采纳**
- 说明：netcode 最简单、最易保证公平与重连，但动作爽感缺失削弱联机吸引力，与主轴不符；保留为 netcode 不达标时的降级兜底路径。

### 附：收口后剩余风险（供 team-lead 排期）
1. **netcode 复杂度（高，MVP 关键路径）**：动作 Roguelike 实时同步 + 客户端预测 + 服务器回正，是本项目最大技术不确定项。建议尽早让程基岩出 ADR：延迟预算（如 RTT 容忍上限）、tick rate、预测/回正策略、反作弊校验点。若 Web 实时同步体验不达标，降级路径为"方案 A 节奏放缓 + 方案 C 回合化兜底"（已在 §7 留痕）。
2. **P3 可读性阈值需程基岩出 ADR**：P3「读得懂的紧张感」依赖延迟宽容与明确预警，须与网络层延迟预算、客户端表现层（预警帧/插值）共同定义可读阈值，否则支柱在体验层落空。
3. **断线重连的状态托管边界**：P4 要求服务器托管掉线玩家角色（冻结/AI 暂代），需在架构层明确"托管期间输入丢弃/状态快照频率/重连归位"的边界，避免重连瞬间的状态跳变劝退。
4. **轻量 Build 与"主导策略"红线的张力**：延展层 Build 系统（装备/perk）若数值设计不当，可能催生单一最优 Build，违反 P2 反主导策略。后续 GDD 须内置 Build 多样性评审。
5. **Lean 评审下的内容量 vs Run 变化**：P2 靠"变化"掩盖内容少，但 MVP 仅 1 生物群系 + 轻量随机，需验证"轻量随机"是否足以支撑重玩，否则需提前评估程序化生成优先级。
6. **跨职能依赖**：§6 像素风规格已锁定，art-director 可据此定稿美术圣经；但队伍强调色/可读性预警的"色盲友好"约束需在美术圣经与 UX 规格间对齐。
