## 1. 结论速览（TL;DR）

| 项 | 结论 |
|---|---|
| **卡顿阈值（服务端）** | **未在 ≤1000 并发观测到卡顿**（到达率恒 100%、RTT p95 ≤ 100ms、0 丢帧）。按 CPU 线性外推，单进程单核饱和约在 **N≈1800**（1500 的实测受压测客户端/本机内存上限，见 §3.2） |
| **12Hz 全量帧广播** | **不是瓶颈**。已是「编码一次、多连接共享同一 Buffer」；无每连接重复编码、无 O(N²) 编码 |
| **world.step / snapshot 序列化** | 计算开销极小：N=300 时 step+snapshot+encode 合计 1.2ms/tick，仅占 83ms tick 预算 **15%** |
| **CPU 主要去向（实测差分）** | 每 tick 的 `ws.send` 扇出（O(N) 次 socket 写），N=1000 时约占总 CPU 55%（线性增长） |
| **服务端代码** | **零改动、零修复**（无临界路径 bug；不盲目优化） |
| **发现一个真实隐患（Phase-2）** | join 期 `room.snapshot` 全房广播为 **O(N³) 字节** + 每次 join 双重广播；连接风暴（数百人同时入房）时控制面流量暴增，压测父进程因此 OOM（详见 §6） |
| **压测脚本** | `games/jianghu/scripts/bench-load.mjs`（新增，`--n` 可配；压测/复测均用它） |

## 2. 压测方法

### 2.1 脚本与用法

```bash
# 自起服务端（:3011，子进程内 process.cpuUsage 采样 CPU/RSS，不依赖 ps）
node --experimental-strip-types games/jianghu/scripts/bench-load.mjs \
  --n 10,30,60,100,150,200,300 --duration 15000 --warmup 5000 --out /tmp/bench.json
# 连外部已运行服务端（无资源采样）
node --experimental-strip-types games/jianghu/scripts/bench-load.mjs --n 100 --no-server --port 3011
```

### 2.2 压测模型

- 每个连接：`room.join` → 持续收 12Hz 二进制快照 → **每 100ms 发一条 MOVE**（活动玩家；目标格随机中心区、每 5s 换向，不同 seat 不同方向/目标）。
- **快照到达率**：测量窗口内收到帧数 / 期望 12Hz×时长。每帧只读帧头 9 字节（O(1)），不整帧解码，避免压测客户端自身成为测量瓶颈。
- **端到端 RTT**：**STOP-first 探针**——暂停 MOVE 循环 → 发 STOP → 解码帧等自己位置连续两帧一致（已停）→ 发 MOVE（换新目标）→ 记 sendAt → 等位置变化帧 → `RTT = 到达 - sendAt`。只在探针窗口内解码（避免 O(实体×连接) 的父进程解码开销）。
- **服务端 CPU/RSS**：压测脚本自起服务端子进程，子进程内每 1s 用 `process.cpuUsage()` 增量 + `memoryUsage().rss` 自报（`[bench-server] STAT` 行），父进程聚合测量窗口均值/峰值。**与压测客户端隔离**（客户端在父进程，CPU 干净归属服务端子进程）。
- **判定（卡顿阈值）**：到达率均值 < 90% **或** RTT p95 > 500ms。
- 每档 N 用**全新服务端进程**（无残留成员/实体），`DEV_SKIP_AUTH` + 内存角色存储，不触 api2、不落磁盘。
- 压测为纯运行时性能路径：不触碰 310 测试 / playtest golden（D9 确定性不涉运行时）。

### 2.3 负载说明（保守性）

所有玩家**全程持续移动**（全量帧的 pos 每 tick 全变 → 帧体积最大化的最坏情形），MOVE 10Hz/人。真实游玩有大量站桩/低活跃玩家，帧更小、头寸更大。

### 3.2 卡顿阈值

- 判定标准：到达率 < 90% 或 RTT p95 > 500ms。
- **实测 N=10…1000 全部通过**，阈值**未达**。CPU 线性外推单核饱和 ≈ **N≈1800**（N=1000 时 57.0%）。
- **N=1500 未能干净测量**：压测父进程（单进程承载 1500 个 ws 客户端，接收 ~990MB/s 二进制帧）被本机 OS OOM-kill（exit 137）——这是**压测客户端 + 本机内存上限**，不是服务端崩溃（服务端 CPU 在 1000 人仅 57%）。
- 结论表述：**MVP 规模（10–100 人，任务要求档位）远低于瓶颈**；「多少人同时在线会卡」在单进程部署下约为 **千五～两千**（外推），且受 CPU 单核限制而非内存/带宽（RSS 到 1000 人仅 ~136–157MB）。要精确定位 1500+ 的服务端阈值，需多进程客户端压测台（Phase-2 工具项，§7）。

## 4. 瓶颈分析（实测驱动，非猜测）

### 4.1 广播路径：已是「编码一次、共享 Buffer」

读代码 + ws 源码核实：

- `run-manager.ts onBroadcast`：`const buf = encodeSnapshot(snapshot); broadcastData(roomId, buf)` —— **每 tick 只编码一次**。
- `connection-registry.ts broadcastToRoom`：对同房连接逐个 `conn.send(buf)` —— **同一 Buffer 引用**，无每连接复制。
- `gateway.ts conn.send`：`ws.send(payload)` 直接透传，无 `Buffer.from` 拷贝。
- `node_modules/ws sender.js`：`Sender.frame(data)` 返回 `[帧头, data]` —— 服务端不掩码、**不拷贝、不改写共享 Buffer**；`socket.write` 只持有引用直至刷出。

结论：**不存在「每连接重新编码 / 每连接复制 Buffer」的 O(N²) 反模式**。候选优化第一项（广播共享 Buffer）**已实现**，无需修改。

### 4.2 计算路径：step / snapshot / encode 微基准（进程内，排除网络）

| N | 实体数 | step | snapshot | encode | 每 tick 合计 | 占 83ms 预算 |
|---:|---:|---:|---:|---:|---:|---:|
| 100 | 103 | 188µs | 11µs | 137µs | 336µs | 4.0% |
| 300 | 304 | 805µs | 38µs | 389µs | 1.23ms | 14.8% |

计算（含玩家全移动的 step、全量 snapshot 对象构建、全量二进制 encode）在 N=300 也仅占 tick 预算 ~15%，**不是瓶颈**。`world.step` 内 `actors.find` 的 O(N²) 形状在千级以下可忽略。

### 4.3 CPU 实测差分（服务端进程）

- 服务端总 CPU（实测）：N=1000 → 57.0%。
- 其中计算（4.2 微基准按 N=1000 外推，step 略超线性，合计 ≈ 6–8%）：
  `12 tick/s × ~5–6ms ≈ 60–75ms/s`。
- 其余 ≈ **50% 为每 tick 的 ws.send 扇出**（N 次 socket 写 / tick × 12Hz）+ ws 心跳 + 事件循环。
- 曲线近线性（10 人 4.2% → 1000 人 57.0%，斜率 ≈ 0.053%/连接）：**瓶颈形态 = 单进程单核的 O(N) 发送扇出**，而非编码/计算/内存/带宽。

### 4.4 结论：12Hz 全量帧在 ≤100 人（甚至 ≤1000 人）内 OK

- 帧体积 N=100 ≈ 3.8KB / N=1000 ≈ 37KB；N=1000 时广播带宽 ≈ 1000×37KB×12 ≈ 444MB/s（loopback 实测 CPU 57%，未到带宽/内存瓶颈）。
- **快照 diff（ChangeBit 已有，只发变化实体）→ 列为 Phase-2**：实测阈值远超 MVP 规模，MVP 期不值得引入 diff 状态追踪的复杂度与回归风险。
- 广播节流（降 12Hz）→ **不推荐**：12Hz 是游戏循环本体（C1 单一来源），非冗余。

## 5. 修复内容（服务端：无；压测工具：3 处）

> 纪律「先测后改，不盲目优化」：实测未在临界路径发现 bug → **服务端代码零改动**。压测脚本本身修了 3 个测量缺陷（属工具修正，非游戏逻辑）：

| # | 缺陷 | 症状 | 修复 |
|---|---|---|---|
| 1 | 客户端 `nextText` 监听器在 open 之后才挂，`session.ready` 同 tick 到达被永久 handler 吞掉 | N≥60 起出现假「加入失败」（expected session.ready got undefined，随 N 升到 6%+） | 永久 handler 改为 MsgQueue 缓冲（同 integration.test.ts 模式），连接创建即挂 |
| 2 | 控制面 `room.snapshot` 全房广播被客户端无界缓冲（join 风暴 O(N³)） | 压测父进程 V8 OOM（N=400/600 崩，3.5GB heap），并污染 RTT（N=400 曾假报 p95 656ms） | 连接完成后丢弃控制面文本（`textDrop`），只保留连接期缓冲 |
| 3 | RTT 探针在「玩家持续移动」下有假阳性（0ms / 帧节奏偏差） | RTT 低估（旧法 p50≈42ms 实为帧节奏） | 改 STOP-first 探针：暂停 MOVE → STOP → 稳定 → MOVE → 测位置变化；只探针窗口解码 |

**修复后复测（同一 N 对比）**：

| N | 修复前（污染） | 修复后（干净） |
|---|---|---|
| 400 | RTT p95 **656ms**、max 3557ms（父进程 GC 抖动假象） | RTT p95 **88ms**、max 97ms、CPU 25%、到达率 100% |
| 600 | 父进程 OOM 崩溃 | RTT p95 89ms、CPU 32%、到达率 100% |

→ 证明：**服务端在 400/600 并发下无卡顿**；早前的 656ms / OOM 均为压测客户端测量缺陷。

## 6. 发现的真实隐患（Phase-2，本次不修）

### 6.1 join 期 `room.snapshot` 全房广播 = O(N³) 字节 + 双重广播

- 路径：`room.join` → `joinResident` → `notifyRoomChanged` → `roomChangeListener` → `broadcastControl(room.snapshot)`（全房）；且 `dispatch` room.join 分支**又显式 push 一次 room.snapshot 广播** → 每次 join 旧成员收到 **2 份**快照。
- 复杂度：join #k 时快照含 k 个成员、发往 k 个连接 → 单 join 控制面字节 O(k²)，**连接风暴总字节 O(N³)**。
- 估算：N=400 ≈ **817MB**；N=1000 ≈ **12.7GB** 控制面流量（实测压测父进程因接收此流量 OOM）。
- 影响评估：正常游玩（成员随时间错峰进出）无感；**仅连接风暴（数百人同时入房，如开服/活动）** 时服务端发送量与客户端接收量暴增。
- **最小修复方案（Phase-2，需主理人批准 + 回归）**：
  1. 去除 join 路径双重广播（joinResident 的通知与 dispatch 显式广播二选一，保留 dispatch 侧使新成员也能收到）——立减 50%；
  2. 根治：join/leave 改用**增量** presence 通知（如 `room.member.joined/left`），或 room.snapshot 仅发往变化的连接——把 O(N³) 降为 O(N)；
  3. 或对 presence 广播做节流/合并（如 500ms 窗口合并多次变化）。
- **为何本次不修**：不在 12Hz 数据面临界路径；实测 N≤1000 服务端表现健康（CPU ≤57%）；改协议/通知语义有客户端回归风险（web-client 依赖 room.snapshot 渲染成员列表），适合作为独立 Phase-2 项带回归测试推进。

## 7. 建议（按优先级）

| 优先级 | 项 | 理由 |
|---|---|---|
| P0 | 无需动作 | 12Hz 全量帧广播 + 单进程服务端在 MVP（≤100 人）远未饱和 |
| P1 | 若真要做（≤1 天）：join 双重广播去重 | 代码 2 行、零协议变化、减 50% 控制面；覆盖现有 room-service 测试即可回归 |
| P2 | join/leave presence 增量通知 | 根治 O(N³)；需新消息类型 + 客户端适配，列独立迭代 |
| P2 | 快照 diff（ChangeBit 已有） | 单人 1000+ 在线才必要；引入 diff 状态追踪/重连补帧复杂度，MVP 不做 |
| P2 | encode 零分配化（BufWriter 预分配单 Buffer） | N=300 时 encode 389µs/tick，非瓶颈；纯 GC 优化，顺路可做 |
| P3 | 多进程客户端压测台 | 单进程客户端在 N≥1000 已成为测量瓶颈（本报告已用「探针窗口解码 + 文本丢弃」缓解）；若要测 1500+，拆客户端 worker 进程 |

## 8. 附：压测过程记录的坑（供后续维护）

1. **`node -e` 起服务端子进程**：需 `--input-type=module`（top-level await）；`stdio` 的 stderr 若用 `inherit` 则 `child.stderr` 为 null，要采样需 `pipe`。
2. **ws 共享 Buffer 安全性**：`Sender.frame` 服务端不掩码不拷贝，`socket.write` 只引用 —— 共享 Buffer 可放心复用（已核实，非隐患）。
3. **RTT 探针必须 STOP-first**：玩家持续移动时「位置变化」与「我的 MOVE 被处理」无法归属，直接测会得到帧节奏假值。
4. **控制面文本不可无界缓冲**：任何「连接期缓冲 + 之后忽略」都要显式 drop，否则 join 风暴把压测客户端打爆（OOM 假象）。
5. **服务端 CPU 采样用子进程内 `process.cpuUsage()` 增量**，比 `ps` 更稳、跨沙箱可用；压测客户端在父进程，CPU 归属干净。
6. **测量窗口首尾帧**会造成 1 帧的到达率 99.5% 假象（180 期望中少 1），判定阈值 90% 足够容忍。
